01

Filosofia da divisão

estratégia

A spec sugere explicitamente: uma pessoa no servidor + cliente CLI, a outra no cliente GUI + world design. É uma divisão limpa, paralelizável e com baixo atrito de coordenação — vamos seguir essa linha, mas com um ajuste para os vossos pontos fortes.

O Rui fica com o motor — servidor, concorrência, protocolo, CLI. É o trabalho de sistemas mais exigente e onde a tua experiência de concorrência em C te dá vantagem direta. O Alexandre fica com a experiência — cliente GUI, desenho do mundo e dados — que tem superfície visual grande e é relativamente independente do interior do servidor. É exatamente o padrão de colaboração que já vos funciona noutros projetos: um no engine, outro na UI/infra.

Regra de ouro da spec
Ambos têm de contribuir significativamente para o código e ter commits no repositório. A divisão abaixo dá donos principais, mas não silos: o pacote protocol é escrito a quatro mãos e cada um deve conseguir explicar o componente do outro na avaliação. Façam pair review dos PRs um do outro.

// Zona partilhada — escrita a quatro mãos, PRIMEIRO de tudo
O pacote internal/protocol é o contrato entre servidor e clientes: structs de comando, códigos de resposta, formatos de evento, (de)serialização. Definam-no juntos antes de qualquer um partir para o seu lado. Mudanças aqui são sempre comunicadas. É também o pacote ideal para testes partilhados.
03

Estrutura do repositório

layout

Layout idiomático de Go (cmd/ para executáveis, internal/ para código não-exportável). Cores: azul = Rui, amarelo = Alexandre, verde = partilhado.

the-answer-protocol/
├── cmd/
│   ├── server/        main.go      # arranque do servidor TCP
│   ├── cli/           main.go      # cliente de linha de comando
│   └── gui/           main.go      # app Fyne, painéis, ligação TCP
├── internal/
│   ├── protocol/      comandos, respostas, eventos, parsing
│   ├── server/        hub.go, client.go, dispatch.go
│   ├── game/          world.go, item.go, combat.go, quest.go
│   └── worldfile/     loader.go, validate.go
├── data/              world.json                       # mundo
├── configs/           (se precisarem)
├── Makefile
├── go.mod / go.sum
└── README.md
Porquê este layout
Os três executáveis em cmd/ partilham o pacote internal/protocol — garante que servidor e clientes falam exatamente a mesma língua (requisito de interoperabilidade da spec). O Rui vive em server/ + game/ + cmd/cli/; o Alexandre em worldfile/ + data/ + cmd/gui/. Como CLI e GUI são ambas Go, podem partilhar a camada de rede sem reescrever lógica. Conflitos de merge ficam raros porque tocam em ficheiros diferentes.

05

Fluxo de Git

colaboração
  • ▸Branch por feature: feat/hub, feat/gui-room-view, feat/world-data. main fica sempre a compilar.
  • ▸Pull Request + review do outro antes de merge. Garante que ambos conhecem o código todo (essencial para a avaliação).
  • ▸Commits frequentes e descritivos: a spec verifica que cada membro tem commits. Nada de um commit gigante no fim.
  • ▸Fechar o contrato do protocol primeiro (structs + signatures + códigos), num PR conjunto. A implementação das funções pode vir depois, em paralelo com o resto do trabalho.
  • ▸.gitignore: binários (bin/), nada de outputs gerados.

Conselho de sequência
Resistam a construir o servidor inteiro antes de ligar o cliente. O vertical slice (Fase 02) — uma ponta à outra com o mínimo — é o que reduz risco: provam cedo que o protocolo, o Hub e os clientes encaixam, e a partir daí cada um itera no seu lado com confiança. Na avaliação vão pedir uma modificação ao vivo: se ambos fizeram review do código todo, isto é trivial.
