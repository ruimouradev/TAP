01

Visão geral & mapa mental

conceitoAmbos

O TAP é, na sua essência, um servidor de rede concorrente com um mundo partilhado. Tudo o resto (combate, quests, NPCs) é lógica de jogo que se constrói por cima. Se acertarem na arquitetura de rede e concorrência, o resto flui.

O coração do sistema é este ciclo: vários clientes ligam-se por TCP → cada um envia comandos de texto terminados em \n → o servidor valida, muta o estado do mundo, e faz broadcast de eventos para os clientes relevantes → tudo isto sem nunca bloquear nem corromper o estado partilhado.

Modelo mental Go
Pensa em três tipos de goroutines: (1) uma que aceita ligações novas, (2) uma por cada cliente ligado (lê comandos desse cliente), e (3) uma única que é "dona" do mundo e processa tudo o que muta estado, em série. Esta última é o truque que elimina quase todos os race conditions.
02

Rede TCP em Go

netRui
▶
Rui: domínio crítico — vais escrever o accept-loop, gerir net.Conn e os erros de rede. Lê toda a secção a fundo + exemplos do net package. Alexandre: só precisas de net.Dial para o bridge (não o servidor); leitura superficial chega.

Go traz tudo na biblioteca padrão. Não precisas de dependências para a rede. O padrão canónico de servidor TCP é:

func main() {
    ln, err := net.Listen("tcp", ":4242")
    if err != nil { log.Fatal(err) }
    defer ln.Close()

    for {
        conn, err := ln.Accept()      // bloqueia até chegar um cliente
        if err != nil { continue }
        go handleConn(conn)          // uma goroutine por ligação
    }
}

O go handleConn(conn) é a magia: cada cliente é tratado em paralelo, sem threads manuais nem select() à C. Comparado com C, isto é uma redução brutal de complexidade — é por isto que Go foi a escolha certa para este projeto.

  • net.Listener — o socket de escuta; Accept() devolve uma net.Conn por cliente.
  • net.Conn — implementa io.Reader e io.Writer. Lês e escreves como se fosse um ficheiro.
  • Sempre defer conn.Close() dentro de handleConn — garante limpeza mesmo com erro/pânico.
03

Modelo de concorrência: o Hub

goroutinesRui
▶
Rui: esta é a secção mais importante para ti. O Hub é o coração do servidor — se não dominares isto, vais ter races para o resto da vida. Lê duas vezes + cap. 8 do Donovan & Kernighan. Alexandre: útil ler para a defesa do código, mas não vais escrever nada disto.

Esta é a secção mais importante do projeto. Há duas abordagens válidas para proteger o estado partilhado:

Abordagem A — Mutex (sync.RWMutex)

Envolves o estado do mundo num sync.RWMutex e cada goroutine de cliente faz Lock() antes de mutar. Funciona, mas é fácil esquecer um lock e introduzir uma race; e o broadcast com lock segurado pode bloquear toda a gente.

Abordagem B — Hub / Actor (RECOMENDADA)

Uma única goroutine é dona do mundo. Os clientes não tocam no estado diretamente: enviam mensagens por channels para o Hub, que processa tudo em série. Isto segue o lema oficial de Go: "Don't communicate by sharing memory; share memory by communicating."

type Hub struct {
    register   chan *Client
    unregister chan *Client
    commands   chan Command   // comando + quem o enviou
    clients    map[*Client]bool
    world      *World            // só o Hub lhe toca
}

func (h *Hub) Run() {
    for {
        select {
        case c := <-h.register:   h.clients[c] = true
        case c := <-h.unregister: h.removePlayer(c)   // remove ANTES do broadcast
        case cmd := <-h.commands:  h.dispatch(cmd)
        }
    }
}
Porque é que isto resolve tudo
Como só o Hub muta o mundo, e processa um evento de cada vez, não existem race conditions sobre o estado do jogo — sem um único mutex. Cada cliente tem ainda uma goroutine de leitura (recebe do socket → manda Command ao Hub) e tipicamente uma de escrita (lê de um channel buffered → escreve no socket). O broadcast nunca bloqueia o Hub se usares channels buffered por cliente.
  • channels — o canal de comunicação entre goroutines; pensa numa fila tipada e segura.
  • select — espera em vários channels ao mesmo tempo; é o coração do loop do Hub.
  • buffered channel por cliente — send chan string com buffer; se o cliente for lento, não trava o servidor (e podes desligá-lo se o buffer encher).
  • Corre sempre com -race durante o desenvolvimento para apanhar acessos concorrentes.
04

Framing & protocolo de linha

RFC 42TAPAmbos
▶
Ambos: o pacote protocol é o contrato partilhado — toca aos dois. O Rui usa-o para parsear/formatar no servidor; o Alexandre usa os mesmos formatos em JS para parsear no GUI. Saber isto a fundo é essencial para a defesa.

O protocolo é line-based, UTF-8, uma mensagem por linha terminada em \n. Em Go, ler linhas é trivial com bufio:

scanner := bufio.NewScanner(conn)
for scanner.Scan() {
    line := scanner.Text()        // uma linha, sem o \n
    cmd  := parseCommand(line)   // "MOVE north" -> Command{Verb:"MOVE", Args:["north"]}
    hub.commands <- Command{Client: c, Raw: cmd}
}
Atenção: limite do Scanner
bufio.Scanner tem um limite default de 64KB por linha e dá erro em linhas maiores. Para mensagens grandes (ex.: payloads JSON de LOOK) aumenta o buffer com scanner.Buffer(buf, maxSize), ou usa bufio.Reader.ReadString('\n'). Documenta a escolha no README.

Para a conformidade com a RFC: define cedo um pacote protocol partilhado entre servidor e clientes, com as estruturas de comando, os códigos de resposta (OK, EVT, ERR) e os formatos de evento. Este pacote é o contrato — quem mexer nele avisa o outro. Lembra-te que a spec exige que os clientes sejam interoperáveis entre grupos, por isso o formato do wire tem de seguir a RFC à risca; só a UI/UX dos clientes é livre.

  • Respostas: OK ... para sucesso, EVT <scope> ... para eventos push, ERR <code> ... para erros.
  • Comando malformado → resposta de erro protocol-compliant, nunca crashar.
  • Dispatcher: um map[string]HandlerFunc mantém o código limpo e escalável face aos ~15 comandos.
05

Estado partilhado do mundo

domainRui
▶
Rui: tu desenhas o modelo World/Room/Player/NPC e todas as mutações. Lê a fundo. Alexandre: útil para perceberes a forma dos dados que envias para o GUI; saltar detalhes de implementação.

Modela o domínio com structs simples. Mantém o estado mutável (jogadores, itens no chão, HP dos NPCs) separado dos dados estáticos carregados dos ficheiros (a planta das salas, definições de itens).

type Room struct {
    ID, Name, Desc string
    Exits map[string]string   // "north" -> roomID
    Items map[string]*Item   // instâncias únicas no chão
    NPCs  []*NPC
    Players map[string]*Player
}

Como decidimos na secção 03 que só o Hub muta o mundo, estas structs não precisam de mutexes. Toda a mutação passa por um handler chamado dentro do loop do Hub. Isto mantém o modelo de domínio limpo e o raciocínio sobre correção é trivial: "uma coisa de cada vez".

06

Desconexões & shutdown gracioso

robustezRui
▶
Rui: o avaliador vai matar clientes a meio de broadcasts e dar Ctrl+C para ver se o server cai — secção crítica para passar "Robustness" na correction sheet. Alexandre: superficial; só precisas de saber que o bridge deve fechar a TCP quando a WS cair.

A spec é explícita: remover o estado do jogador ANTES de fazer broadcast do evento de saída, e o servidor tem de continuar a transmitir a outros mesmo que um cliente desligue a meio do envio.

  • Quando scanner.Scan() devolve false (cliente desligou), a goroutine envia hub.unregister <- c e termina (via defer).
  • O Hub remove o jogador da sala/mapa e só depois faz broadcast de EVT ROOM PRESENCE LEAVE.
  • Escritas para clientes lentos/mortos não podem travar o Hub: usa select com default ou um channel buffered por cliente; se a escrita falhar, desliga esse cliente, mas continua os outros.
  • Shutdown limpo: signal.NotifyContext(ctx, os.Interrupt) + um context.Context propagado fecha o listener e as goroutines de forma ordenada no Ctrl+C.
Idioma Go: errors são valores
Em Go não há exceções. Verifica err sempre. Para fluxo de controlo de shutdown, usa context. Reserva panic/recover só para falhas irrecuperáveis — e protege as goroutines de clientes com recover para que um bug num cliente nunca derrube o servidor inteiro.

Dados do mundo (YAML / JSON)

loaderAlexandre
▶
Alexandre: domínio crítico — tu escreves o worldfile (loader + validator) e desenhas o world.json. Lê a fundo. Rui: útil para perceberes a forma dos dados que carregas para o game.World, mas o parsing é dele.

A spec aceita YAML ou JSON. Recomendo JSON para começar — está na biblioteca padrão (encoding/json), zero dependências. Se preferirem YAML pela legibilidade, usem gopkg.in/yaml.v3.

type WorldFile struct {
    Locations map[string]RoomDef `json:"locations"`
    Items     map[string]ItemDef `json:"items"`
    NPCs      map[string]NPCDef  `json:"npcs"`
}
data, _ := os.ReadFile("data/world.json")
var wf WorldFile
json.Unmarshal(data, &wf)

Crucial (requisito da spec): validar todas as saídas e referências depois de carregar. Antes de aceitar clientes, percorre todas as salas e confirma que cada exit aponta para uma sala existente, que cada item/NPC referenciado existe. Falha cedo e com mensagem clara se o mundo for inconsistente — é exatamente o tipo de robustez que distingue um projeto bem feito.

Requisitos mínimos do mundo a desenhar: ≥8 salas interligadas formando loops (circuito completo, não linha) + 1 ramo opcional, ≥3 papéis de NPC, ≥4 itens (≥2 obteníveis), ≥2 quests.

Itens, combate & quests

game logicRui
▶
Rui: toda a lógica de jogo é tua. As decisões de design (fórmula de damage, mecânica de quests) têm de ser documentadas no README e defendidas na avaliação. Alexandre: precisas de perceber as decisões para renderizar combate/quests no GUI e para responder em defesa.

Sistema de itens

  • Itens são instâncias únicas — TAKE remove da sala (sem duplicar), DROP devolve à sala.
  • Resolução por ID ou nome, com suporte a nomes multi-palavra ("rusty key"). Normaliza para lowercase ao comparar nomes.

Combate (decisão de design — documentar no README)

A spec deixa as mecânicas ao vosso critério mas exige: jogadores começam com 100 HP, NPCs inimigos com HP variável, ATTACK causa dano e pode gerar contra-ataque, STATUS mostra HP, jogador a 0 HP renasce num local seguro com HP reduzido, resultados de combate logados e transmitidos. Documenta a fórmula de dano, ordem de iniciativa e comandos extra (DEFEND, FLEE) — manter simples e determinístico facilita a defesa na avaliação.

Quests (decisão de design — documentar no README)

≥2 quests simples (fetch item, derrotar NPC, entregar item). Modela o progresso por jogador como uma máquina de estados pequena: NotStarted → Active → Completed. Define explicitamente a validação de conclusão e o sistema de recompensa.

Logging estruturado

log/slogRui
▶
Rui: a correction sheet tem 10 pontos só sobre logging — secção crítica. Lê a fundo + define cedo as conventions (campos, níveis). Alexandre: só precisas de saber que o servidor faz log estruturado em stdout; não escreves nada do logging.

A spec exige logging estruturado (JSON recomendado), com níveis INFO/WARN/ERROR, timestamps precisos, e cobrindo conexões, comandos, respostas, mudanças de estado, quests e padrões de abuso. Go tem isto na stdlib desde a 1.21: log/slog.

logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
logger.Info("command",
    "player", p.Name, "verb", cmd.Verb,
    "args", cmd.Args, "ip", conn.RemoteAddr())
  • Cada linha de log é um objeto JSON — fácil de fazer grep/parse, exatamente o que a spec pede.
  • Níveis: slog.Info / slog.Warn / slog.Error.
  • Para detetar abuso (flooding de comandos, conexões rápidas), conta eventos por cliente numa janela temporal e loga WARN ao ultrapassar um limiar.
  • Logging não pode degradar performance: o handler do slog é eficiente; evita formatar strings caras se o nível não for emitido.

Clientes CLI & GUI

clientsAmbos
▶
Rui: domina as subsecções Cliente CLI e duas goroutines de I/O. Alexandre: domina Cliente GUI, Bridge HTTP/WebSocket e Front-end — o resto do GUI é todo teu.

Cliente CLI Rui

O desafio: continuar a receber eventos do servidor enquanto espera input do utilizador. Solução idiomática em Go — duas goroutines:

go func() {                          // goroutine: lê do servidor e imprime
    s := bufio.NewScanner(conn)
    for s.Scan() { fmt.Println(s.Text()) }
}()
in := bufio.NewScanner(os.Stdin)   // main: lê do teclado e envia
for in.Scan() { fmt.Fprintf(conn, "%s\n", in.Text()) }

A spec permite duas abordagens: enviar comandos RFC crus, ou um CLI amigável que traduz para pacotes RFC nos bastidores. Documenta a escolha.

Cliente GUI Alexandre

Recomendação forte
GUI nativo em Go é o ponto fraco da linguagem. A jogada limpa é um GUI web (a spec permite explicitamente "web-based"): um pequeno servidor HTTP em Go serve uma página, e um bridge WebSocket↔TCP fala com o servidor TAP. Toda a stack fica em Go e evitas lutar com toolkits nativos. Alternativa nativa razoável: Fyne (fyne.io), mas é mais trabalho. Nota: curses conta como texto, não como GUI.

O GUI tem de mostrar sala/itens/NPCs/saídas com updates em tempo real, inventário, botões para todas as ações, separar chat (Global/Room/Group) do log, e contadores de jogadores na sala/servidor.

Bridge HTTP/WebSocket (lado Go) Alexandre

O bridge é um binário Go que faz duas coisas: (1) serve os ficheiros estáticos (index.html, app.js, style.css) por HTTP; (2) aceita conexões WebSocket do browser e abre uma conexão TCP correspondente ao servidor TAP, fazendo relay bidirecional dos bytes. Não parseia o protocolo — é só um cano.

// cmd/gui/main.go — esqueleto
func main() {
    http.Handle("/", http.FileServer(http.Dir("web")))  // 1. servir estáticos
    http.HandleFunc("/ws", handleWS)                          // 2. endpoint WS
    log.Fatal(http.ListenAndServe(":8080", nil))
}

func handleWS(w http.ResponseWriter, r *http.Request) {
    ws, _ := websocket.Accept(w, r, nil)                // upgrade HTTP → WS
    tcp, _ := net.Dial("tcp", "localhost:4242")        // abrir TCP para o TAP
    go relayWStoTCP(ws, tcp)                              // browser → server
    relayTCPtoWS(tcp, ws)                                 // server → browser
}
  • net/http — biblioteca standard. http.FileServer serve uma pasta inteira; http.HandleFunc regista endpoints. ListenAndServe bloqueia até crashar.
  • Biblioteca WebSocket — não está na stdlib. Escolhe entre nhooyr.io/websocket (moderna, recomendada) ou gorilla/websocket (clássica). Instala com go get. Ambas têm um echo server no README — usa-o como ponto de partida.
  • net.Dial — abrir uma conexão TCP como cliente (o oposto de net.Listen). Devolve uma net.Conn que se usa exatamente como a do servidor.
  • Padrão de relay (duas goroutines) — uma copia WebSocket → TCP, outra TCP → WebSocket. Quando uma falha (cliente fecha o browser, servidor cai), fecham-se as duas conexões e ambas as goroutines saem. Não te esqueças do framing: o TCP é line-based (\n), o WS é message-based — cada mensagem WS deve corresponder a uma linha TCP.
  • Linha vs mensagem — do lado TCP usa bufio.Scanner para ler linha-a-linha e envia cada uma como mensagem WS. Do lado WS, lê mensagem inteira e escreve no TCP terminando com \n.
Cuidado com o origin/CORS
Por defeito, as libs WebSocket bloqueiam origens diferentes. Se servires o HTML em :8080 e o WS em :8080 não há problema (mesma origem). Mas se separares, terás de passar InsecureSkipVerify (nhooyr) ou um CheckOrigin que retorne true (gorilla) durante o desenvolvimento.

Front-end (HTML/JS/CSS) Alexandre

Sai do âmbito deste documento (que é teoria Go), mas em resumo o app.js precisa de: ligar via new WebSocket("ws://localhost:8080/ws"), fazer JSON.parse nas respostas que o servidor envia, manipular o DOM para renderizar a sala/inventário/chat, e enviar comandos com ws.send("MOVE north\n"). Build, lint & testes

toolingAmbos
▶
Alexandre: o Makefile é teu — garante que make deps/run-server/run-client/run-client-gui/lint/clean funciona sempre. Rui: escreve testes do protocol e da lógica de mundo. Ambos: correr com -race antes de cada PR.

A spec exige um build tool com alvos: instalar dependências, run-server, run-client, run-client-gui, lint, clean. Em Go: Go modules + um Makefile fino por cima.

# Makefile
deps:        ; go mod download
run-server:  ; go run ./cmd/server data/world.json
run-client:  ; go run ./cmd/cli localhost:4242
run-client-gui: ; go run ./cmd/gui
lint:        ; gofmt -l . && go vet ./... && golangci-lint run
clean:       ; go clean && rm -rf bin/
  • go mod init arranca o módulo; dependências são automáticas via go.mod/go.sum.
  • gofmt — formatação não é negociável em Go; corre sempre. go vet apanha bugs comuns. golangci-lint é o linter agregado standard.
  • Testes: ficheiros _test.go + go test ./.... Testa o pacote protocol (parsing/serialização) e a lógica do mundo sem rede. Para multiplayer, escreve um teste que liga 2+ clientes via net.Dial e verifica eventos.
  • Corre o servidor e os testes com -race regularmente.

Armadilhas de Go (vindos de C/Python)

gotchasAmbos
▶
Ambos: leitura rápida obrigatória. Estes erros acontecem aos dois e podem custar horas de debugging. Voltem aqui quando algo "não devia estar a falhar".

Vindos de Python (mais comuns para vocês)

  • Erros são valores, não excepções — em Python apanhas com try/except; em Go cada chamada que pode falhar devolve (result, error) e tens de verificar if err != nil à mão, todas as vezes. Não há raise. panic existe mas é para situações inrecuperáveis, não para fluxo normal.
  • Tipos estáticos, sem Any — não dá para meter um int onde se espera string. Sem duck typing. Para "qualquer tipo" usa-se any (alias de interface{}), mas tens de fazer type assertion para usar: v.(string).
  • Não há list comprehensions nem map/filter — sente-se a falta no início. Em Go escreves um for range normal e append ao slice. É mais verboso mas mais legível.
  • nil ≠ None — só pointers, slices, maps, channels, interfaces e funções podem ser nil. int, string, bool nunca são nil (têm zero-values: 0, "", false).
  • Bool estrito — if x não funciona com strings ou números como em Python. Tem de ser uma expressão booleana: if x != "", if x > 0, etc.
  • Concorrência real (sem GIL) — goroutines correm em paralelo de verdade em múltiplos cores. O preço: race conditions são possíveis. Daí o padrão Hub e o -race detector.
  • Maps escritos em paralelo dão crash — em Python o GIL protege. Em Go, dois goroutines a escrever no mesmo map ao mesmo tempo: panic. Daí o Hub ser o único dono do mundo.
  • Sem REPL prático — não há python -i equivalente. O ciclo é go run file.go ou testes (go test). Aprende a usar testes como REPL.
  • Strings são bytes UTF-8 — iterar com for i := range s dá bytes; com for _, r := range s dá runes (caracteres Unicode). Diferente de Python onde for c in s dá sempre caracteres.
  • Sem keyword arguments — funções aceitam só argumentos posicionais. Para "named args" usa-se um struct de opções.
  • Indentação não é sintaxe — chavetas mandam. Mas o gofmt formata por ti, não há discussão de estilo.

Vindos de C (também aplicáveis)

  • Não há ponteiros aritméticos — esquece p++ ou p + n. Slices substituem quase todos os casos.
  • Garbage collector existe — não chamas free(); o GC trata da memória. Mas atenção a leaks lógicos: goroutines que ficam vivas, referências em maps que nunca apagas.
  • Slices partilham array subjacente — fatiar um slice cria uma view, não uma cópia. Modificar uma fatia altera o original. Em dúvida: copy().
  • nil maps dão panic ao escrever — var m map[string]int; m["x"] = 1 crasha. Tens de fazer m := make(map[string]int) ou m := map[string]int{}.
  • defer em loop — defers correm no fim da função, não da iteração. Não acumules defer conn.Close() num for infinito.
  • Não há macros nem preprocessador — Go não tem #define. Usa constantes ou funções inline pequenas.
  • Headers não existem — exportação é por capitalização: Foo é público, foo é privado ao pacote.

Específicas de concorrência (críticas para o servidor)

  • Variável de loop capturada em goroutine — clássico. Em Go <1.22 tens de copiar a variável (x := x) antes do go func(). Em 1.22+ está resolvido, mas confirma a versão.
  • Goroutine leaks — uma goroutine que bloqueia para sempre num channel nunca morre. Garante saída via context ou fecho de channel.
  • Deadlock em channels não-buffered — enviar sem ninguém a receber bloqueia. O padrão Hub + channels buffered por cliente evita isto.
  • Não ignores erros com _ só para compilar — trata-os; é metade da disciplina de Go.
